# Minecraft Explorer — Codex 完整开发提示词

> 使用方式：将本 Markdown 文件作为项目需求文档提供给 VS Code 中的 Codex，并让 Codex 在当前工作区从零创建项目。请按文末的开发阶段逐步实现和验证，不要在尚未完成基础功能时优先制作演示界面。

---

## 0. 你的角色与最终目标

你是一名经验丰富的 Rust、Windows 原生桌面软件、Slint GUI、SQLite 和 Minecraft Java 文件格式开发工程师。请帮助我**实际开发、编译、测试并交付**一个可在 Windows 10/11 上运行的轻量级 `.exe` 程序，暂定名 **Minecraft Explorer**（项目内名称可配置）。

它面向有很多 Minecraft Java 版本、不同启动器实例、大量游戏地图（存档）、资源包、模组、光影包的玩家。

**最核心的使用场景：**我曾经在某个 Minecraft 版本中玩过一张地图，但后来忘记该地图位于哪个版本的 `saves` 文件夹。我希望打开本程序，直接搜索所有游戏目录中的地图名称，看到它属于哪个游戏实例、放在哪个真实文件夹、占用多少空间、最后游玩时间，并一键打开位置或安全管理，而不是逐个打开 `versions` 子目录查找。

产品定位是**Minecraft Java 文件与存档的全局可视化管理器 + 现有 Minecraft 启动器的快捷启动控制台**。这不是重新开发 Minecraft 启动器：用户可以在本程序中快速找出地图所属的游戏目录，并**从地图或版本页面选择 PCL2 / HMCL 启动对应的 Minecraft 版本**。必须尽量复用用户原有启动器的账号登录、Java 环境、内存设置、游戏资源和版本隔离配置。**不自行实现账号登录，不接管、导出或读取账号令牌，不擅自修改启动器配置。**

“打开 PCL2 / HMCL”“选中或定位指定版本”“让 PCL2 / HMCL 实际启动指定版本”是**三种不同能力**，必须在界面、逻辑和测试中明确区分。**第一阶段至少实现启动器路径管理、版本关联和可靠地打开启动器；真正的一键启动指定版本属于优先级很高的后续核心任务，必须先验证启动器的外部调用方式后再实现，不能假装点击后成功启动了指定版本。**

开发原则：

1. **轻量**：单机、离线优先，无 Electron、无内嵌网页前端、无常驻云服务。
2. **流畅**：启动迅速、列表滚动流畅、窗口缩放顺畅，扫描大目录时 UI 不冻结。
3. **易用**：遵循 Windows 桌面交互习惯；搜索、排序、筛选、预览、右键菜单、快捷键合理。
4. **可靠**：绝不误删存档；文件操作必须有保护、确认、失败回滚或明确恢复途径。
5. **真实可用**：禁止拿硬编码示例数据冒充扫描结果；遇到不支持的格式要在界面如实告知。
6. **维护性**：明确的模块分层、可测试的核心逻辑、必要注释与完整构建说明。
7. **启动器兼容性**：优先通过已证实且可维护的方式调用 PCL2、HMCL；不为了“一键启动”破坏它们现有的账号、实例和运行设置。

## 1. 指定技术栈

优先使用下列技术；遇到兼容性或编译问题，请先分析原因并记录调整理由，不要擅自把整个项目换成 Electron 或 Python。

| 职责 | 选型 |
| --- | --- |
| 开发语言 | Rust（稳定版） |
| UI 框架 | Slint（稳定兼容版本） |
| Windows 发布 | x86_64 Windows 原生 `.exe` |
| 数据持久化与查询 | SQLite，`rusqlite` 等适合的轻量库 |
| 并行扫描 | Rust 标准线程 / rayon；可使用消息通道更新 UI |
| NBT 解析 | `fastnbt` 或同类成熟库，搭配 gzip 解压 |
| JSON / TOML | `serde`、`serde_json`、`toml`（按需） |
| ZIP/JAR 读取 | `zip`（只读元数据优先） |
| 文件变动监控 | `notify`（可在后续阶段接入） |
| 文件哈希 | `blake3` 或同类方案，仅按需计算 |
| 日志 | `tracing` / `log`（按需） |
| Windows 回收站 | 合适且受维护的 Windows API 封装/库，需验证实际行为 |
| 启动器进程调用 | `std::process::Command`、Windows Shell API（按已验证的目标启动器行为选取）；避免默认通过 `cmd /C` 拼接命令 |
| 启动器集成 | 定义独立 Adapter/Provider 接口，首批支持 PCL2 和 HMCL；能力与版本兼容性需实测 |

**UI 目标**：原生窗口、现代 Windows 11 风格、优先深色主题并可扩展浅色主题；使用 Slint 的声明式组件体系。优先选择能兼顾运行时依赖、体积、渲染效果的渲染后端，实测后再决定是否指定 FemtoVG。兼容 Windows 高 DPI、窗口缩放和中英文文件名。注意 Slint 的实际发行与署名许可要求，检查依赖许可证并在项目文档中说明。

**构建目标**：提供 Release 构建方式，尽量发布为无需另行安装程序的便携式 EXE；不要声称一定完全“零系统依赖”，应真实说明 Windows 运行环境限制。应用数据（缓存、日志、配置）与 Minecraft 原始文件严格分开。

## 2. Minecraft 目录结构：必须正确处理

**不要假定每个 `versions/<版本名>/` 下都有 `saves`、`mods` 和 `resourcepacks`。**

常见情况 A：未隔离的共享游戏目录：

```text
.minecraft/
├── versions/
│   ├── 1.21.11/
│   └── 26.2-Fabric_0.19.3/
├── saves/
├── resourcepacks/
├── mods/
├── shaderpacks/
└── screenshots/
```

常见情况 B：版本隔离/实例目录：

```text
.minecraft/
└── versions/
    ├── 1.21.11-Fabric_0.19.3/
    │   ├── saves/
    │   ├── resourcepacks/
    │   ├── mods/
    │   ├── shaderpacks/
    │   └── screenshots/
    └── 26.2-Fabric_0.19.3/
        ├── saves/
        ├── resourcepacks/
        └── mods/
```

此外，还可能存在：

- 官方启动器配置指定的自定义 `gameDir`；
- PCL2、HMCL 等启动器对应的实例/隔离目录；
- 多个互不相同的 `.minecraft` 根目录；
- 使用任意中文、英文或自定义名称的版本/实例文件夹；
- 普通版本与 Fabric / Forge / NeoForge / OptiFine 等版本；
- 数据包通常位于 `<世界目录>/datapacks/`，不是版本根目录；
- 有些世界位于自定义游戏目录，不一定归属于 `versions` 下的某个文件夹。

因此请设计明确的数据模型，区分：

1. **Minecraft 根目录（Root）**；
2. **版本定义（Version Definition）**：版本 ID、JSON/JAR 等核心文件；
3. **实际游戏目录（Game Directory / Instance）**：存档、模组等实际存放位置；
4. **共享游戏目录（Shared Game Directory）**；
5. **文件条目（Item）**：世界、资源包、模组、光影包、数据包等；
6. **路径归属（Ownership）**：条目对应的真实物理路径、根目录、游戏实例或共享目录；
7. **启动器安装（Launcher Installation）**：启动器类型、可执行文件路径、工作目录、支持的 Minecraft 根目录以及可用启动能力；
8. **启动映射（Launch Mapping）**：某个游戏实例与某个启动器可启动的具体版本/实例 ID 的关联；用户手动建立的关联需要标明来源。

不能把“某张地图存放在哪个实例里”和“该地图最后使用了哪个 Minecraft 游戏版本”混为一谈。界面默认展示**实际存储位置/所属游戏目录**；能可靠识别游戏版本时再单独展示版本信息。

### 目录发现与路径归属规则

- 初次启动提供「选择 Minecraft 根目录」；可尝试识别常见目录，但用户必须能够自行添加多个根目录、自定义实例目录。
- 若能可靠读取官方启动器配置，可解析其自定义 `gameDir`；若启动器配置不支持或无法确定，不要猜测，提供手动关联游戏目录的功能。
- 不要依据文件夹名硬编码 Minecraft 版本号；优先解析版本 JSON 的 ID、`inheritsFrom` 等元信息，但要容忍非标准版本和命名。
- 不要把所有版本都自动映射到同一个 `saves`，也不要把共享目录中的同一个存档重复统计到所有版本。
- 支持 Windows 绝对路径、空格、中文、长路径等合理场景。遇到不可访问目录要提示但继续扫描其他项目。
- 对符号链接、junction、重解析点采用默认不递归跟随的保守策略，以防无限循环、重复统计或误删到根目录以外；如以后开放跟随选项，必须额外实现去重和安全保护。
- 对未知/自定义结构标记为“未识别实例”并保留路径信息，允许手工分类/关联，而不是直接忽略。
- 启动器可配置不同 Minecraft 根目录或多个实例库。**文件夹名字相似不等于可被当前启动器启动**；建立映射时要同时考虑实际根目录、启动器当前指向的游戏目录、版本/实例 ID。
- 不要将 `level.dat` 中记录的世界历史游戏版本直接当作启动目标；“世界的数据版本”和“当前实际所属实例”可能不一致。

## 3. 产品主要页面

### 3.1 总览 Dashboard

设计左侧导航栏 + 顶部全局搜索框 + 主内容区 + 可选右侧详情面板。

侧边栏最少包含：

- 总览
- 游戏版本 / 游戏实例
- 全部存档
- 全部资源包
- 全部模组
- 全部光影包
- 空间分析
- 清理与备份（可在后期完善）
- 设置
- 启动器管理（可放在设置中，提供 PCL2 / HMCL 路径、实例关联与验证状态）

总览显示真实扫描结果：根目录数、版本/实例数、存档数、资源包数、模组数、可统计磁盘占用；显示最近游玩的世界或最近修改项目，以及扫描状态。**初次扫描期间展示进度与部分结果，不要展示伪造统计数据。**

### 3.2 全部存档（最重要，第一优先级）

跨全部已添加的根目录、全部版本隔离目录、全部共享目录，汇总地图列表。每项尽可能展示：

- 世界图标（优先 `icon.png`，缺失时使用默认图标）；
- 世界名称（优先读取 `level.dat` 中 `Data.LevelName`）；
- 实际存档文件夹名称；
- **所在游戏目录/实例/版本关联**，支持一键定位；
- 世界总占用空间（字节换算及准确/计算中状态）；
- 最后游玩时间（优先 `level.dat` 的 `Data.LastPlayed`）；
- 世界内部声明的游戏版本（可获取时，例如 NBT 中相应字段）；
- 完整物理路径；
- 收藏状态、用户标签（可以在后续阶段加入）。

功能要求：

- 模糊搜索世界名、目录名、关联的版本/实例名、路径；
- 可按名称、**体积大小（升序/降序）**、最后游玩时间、所属版本排序；
- 可按根目录、实例、游戏版本、更新时间筛选；
- 搜索与排序无需每次重新读取所有地图文件；使用 SQLite 缓存与索引；
- 选中显示详情，支持复制真实路径、在文件资源管理器中打开/定位；
- 右键菜单：查看详情、打开所在目录、复制路径、**使用 PCL2 启动所在实例、使用 HMCL 启动所在实例**（仅当映射和对应能力可用）、重命名、复制到其他游戏目录、移动到其他游戏目录、备份、删除（分阶段实现）；
- 世界详情页显示“关联游戏实例”和“启动游戏”入口：按钮的作用是**启动该世界所在的 Minecraft 游戏实例，不默认直接进入单人游戏世界**；若没有已验证的一键进世界方案，不得谎称支持自动进入指定世界；
- 允许同名地图在不同目录同时存在，必须展示区别，不要通过名称去重。

NBT 解析需考虑 `level.dat` 常见 gzip 压缩、缺失、损坏、NBT 版本差异。必要时尝试 `level.dat_old` 恢复读取基础信息，但**不要擅自覆盖原文件**。如果无法解析，仍将文件夹纳入列表，使用目录名与文件系统时间作为**明确标注的替代信息**。时间单位要正确处理，避免把毫秒 Unix 时间戳当作秒。

### 3.3 版本 / 实例管理

主列表字段：版本/实例名称、关联 Minecraft 版本、Mod Loader（可识别时）、目录类型（独立/共享/未知）、路径、实例自身占用空间、最后修改时间。

支持按名称、大小、时间排序和搜索，详情可进入：

- 存档 `saves`；
- 资源包 `resourcepacks`；
- 模组 `mods`；
- 光影包 `shaderpacks`；
- 截图 `screenshots`；
- 数据包（通过该实例关联的世界查看）；
- 其他目录与文件。

每类显示数量与总大小，支持快速跳到全局列表中的对应筛选结果。区分**版本核心文件大小**、**该实例独立游戏目录大小**、**共享目录占用**，避免双重计数与概念混淆。

版本与实例列表、详情页都要有 **「启动游戏」** 操作；若安装了两个启动器，应能选择用 PCL2 或 HMCL 启动，并可设置该实例的默认启动器。若当前启动器没有安装、缺少对应实例、映射冲突或不支持可验证的外部启动，必须禁用“一键启动”并解释原因，提供“打开启动器”和“设置关联”等备选操作。

### 3.4 资源包 / 模组 / 光影包

为每种类型建立跨目录列表，统一支持搜索、排序、路径定位、详情查看及安全文件操作。

- 资源包：列出文件/目录形式的资源包；尽可能读取 `pack.mcmeta` 的描述和兼容性字段、`pack.png` 封面；容忍新版/旧版格式差异。
- 模组：读取 JAR 内可用的 `fabric.mod.json`、`META-INF/mods.toml`、`META-INF/neoforge.mods.toml` 等元信息；未知类型显示文件名和位置，**不要仅依据 JAR 文件名臆造 ID/版本**。
- 光影包：以 ZIP/目录和其文件系统元数据为基础，不强制读取不稳定的第三方特定格式。
- 数据包：从各世界的 `datapacks` 扫描，后续添加全局数据包页面；支持 ZIP/目录与 `pack.mcmeta` 基本信息。

扫描 JAR/ZIP 时仅按需读取指定元数据文件，不要把大型压缩包完整解压到磁盘；对损坏、超大、加密压缩包优雅降级。若未来支持解压，必须防御 ZIP 路径穿越。

### 3.5 全局搜索

顶栏一个搜索入口，搜索范围至少包括版本/实例、世界、资源包、模组、光影包。

- 支持中文、英文、部分名称、文件夹名称和路径匹配；
- 搜索结果按照类型分组或显示类型标签；
- 显示**项目真实存放位置**及关联实例，便于找回忘记放在哪个版本的地图；
- 点击结果可进入详情，双击或快捷操作可在系统文件资源管理器定位；
- 数据量大时搜索应在后台/SQLite 查询完成，避免阻塞界面；可做简短输入防抖；
- 第一版先保证高质量的关键词搜索和排序，再视实际需要增加高级语法、拼音搜索。

### 3.6 空间分析（WinDirStat 风格）

后续阶段加入交互式 **Treemap 矩形树图**：

- 矩形面积对应统计的文件/目录大小；
- 不同颜色区分世界、资源包、Mod、光影包、其他文件；
- 悬停显示完整名称、实际路径、真实大小与归属；
- 点击选中并联动文件列表，双击钻取文件夹，右键打开位置；
- 支持按整个根目录或某个实例分析；
- Treemap 不得在每次鼠标移动时重扫磁盘；大小数据缓存、布局结果复用；
- 文件过多时使用阈值合并小矩形、分层绘制或其他可解释方案，避免创建数万独立可交互控件造成卡顿；
- 必须明确说明共享内容在磁盘总占用中只算一次。

**重要：Treemap 是第二/第三阶段，不要为了先做炫酷图形推迟“全局查找所有存档”功能。**

## 3.7 PCL2 / HMCL 启动器集成（新增核心需求，必须完成设计与分阶段实现）

### 用户的实际操作流程

1. 在「全部存档」搜索地图名，比如“勇者传说”，看到该地图真实路径、存档大小和**实际所属游戏实例**。
2. 选中地图后，右侧有 **「启动所在版本」** 主按钮；如果有多个启动器，点击下拉菜单可以选择 **「通过 PCL2 启动」** / **「通过 HMCL 启动」**。
3. 程序用已确认的 **实例 ID + Minecraft 根目录 + 启动器安装** 映射选择正确目标，绝不能只匹配 `1.21.11` 这样的基础版本号，因为同一个基础版本可能有 Fabric / Forge / NeoForge 和多个完全不同的自定义实例。
4. 符合“可靠直接启动”条件时执行对应启动器的集成调用，并清晰显示“启动请求已发送/启动器运行中/游戏进程已确认启动（如果确实可以检测）/启动失败”等**可验证**的状态。
5. 如当前启动器缺乏受支持且经过验证的**外部指定实例启动**能力：按钮清晰变成「打开 PCL2」或「打开 HMCL」，提示“无法自动为你选择或启动指定版本”，并展示应选择的实例名称与一键复制名称；不允许默默退化为启动默认版本。
6. 用户也能从「游戏版本」列表直接对选中版本使用相同操作。若目标世界仅位于共享 `saves`，而不能唯一确定运行它的实例，需要**让用户选择目标版本**，可保存其手动映射，绝不自动猜测。

### 启动器识别与设置

- 设置 → 启动器管理：列出 PCL2、HMCL，可自动尝试发现，但支持手动选择启动器安装文件路径及工作目录，允许各有多个安装副本。
- PCL2 使用用户选定的真实 `.exe`；HMCL 同时考虑 `.jar`、Windows `.exe` 等可能的发行方式。对 `.jar` 使用用户指定或检测到的**用于启动 HMCL 的 Java 环境**，不擅自使用某个 Minecraft 实例的 Java。
- 记录每个启动器对应的 Minecraft 根目录、实例库（若能可靠探测）、已验证能力和最后一次检测时间；多个启动器可指向同一根目录，也可以分别管理不同根目录。
- 若扫描结果与启动器实际可用的实例列表不能可靠匹配，在 UI 上显示「需关联」并提供用户手动选择，而非靠字符串相似度直接关联。
- 支持全局默认启动器与**每个实例自定义默认启动器**。找不到启动器文件、工作目录不正确、Java 不可用时弹出可操作的错误信息。
- 不需要用户重新输入微软账号密码，不读取、不展示、不复制 PCL2/HMCL 的登录凭据；应由原启动器完成授权、离线账号选择及所有身份验证。

### 对外调用与能力边界（请先核查当前版本，再实现）

- 为两款启动器各实现独立 Adapter，例如 `LauncherAdapter`，能力项建议定义为 `OpenLauncher`、`SelectInstance`、`LaunchInstance`、`TrackGameProcess`；**能力检测不等于能力存在**，应依据版本与实测结果明确给出支持或不支持。
- **PCL2**：其“自定义事件”文档记载了启动器**内部**可以通过“启动游戏”事件指定 `versions/版本目录`。但不能因此推断外部程序拥有对应 CLI、IPC 或 URL Scheme 接口。Codex 必须查看当前可用的 PCL2 官方文档、源码/可用接口，并做外部进程调用测试；内部按钮事件不能直接当作外部 API。不得偷偷修改 PCL2 自定义主页以伪造集成功能。
- **HMCL**：公开文档确认可以启动 HMCL 本体，也有内部实例启动流程；但**启动 HMCL 的 JVM 参数并不等于“从外部指定实例并启动游戏”的公开 API**。Codex 必须先核实指定版本可否通过受支持的命令行参数、IPC、协议或其他官方方式触发，再开放真正的 `LaunchInstance`。
- 若没有可靠外部接口，优先提供明确的“打开启动器 + 告知用户要选择的实例”降级方案；可在文档中记录研究结果与实现限制，**不得**通过模拟点击屏幕坐标、强制修改账号文件/启动器配置、复用登录令牌、注入进程、重新实现不安全的 Minecraft 启动链路来冒充一键启动。
- 有些启动器的接口可能因版本升级变化：集成应模块化、易替换、可禁用，并在发布说明里注明支持的启动器版本和已测试的调用方式。
- 启动目标必须按**真实路径和明确的实例映射**进行校验；PCL2 和 HMCL 可能具有不同的目录隔离规则，绝不只根据世界 `Data.Version.Name` 或文件夹展示名称组装启动命令。
- 以进程 API 的程序路径与参数数组创建进程，正确处理中文路径、引号、空格、启动器工作目录；不要把文件名插进 `cmd /c`、PowerShell 字符串中做不受控的命令拼接。
- 不要阻塞 Slint UI 线程等待启动器；不要对仍在运行的 Minecraft 游戏自动进行世界移动、重命名或删除。尽可能检测使用中状态，无法可靠检测时要求用户确认并说明风险。

### 启动状态与用户反馈

- `LauncherNotConfigured`：未配置 PCL2/HMCL，提供「选择启动器位置」。
- `Unmapped`：已找到世界，但尚未确定关联游戏实例/启动器。
- `OpenOnly`：只能可靠打开启动器，**不能自动启动指定版本**。
- `ReadyToLaunch`：已验证对该启动器与目标实例具备直接调用能力。
- `LaunchRequested`：已调用启动接口；**不等于**游戏已经启动成功。
- `GameRunning`：只有在真实可靠地确认游戏进程属于目标实例时才显示。
- `Failed`：明确失败原因，并能回退至打开启动器或定位实例。

### 模块与数据设计

建议新增：

```text
src/launcher/
├── mod.rs
├── adapter.rs             # 启动器能力/统一调用抽象
├── discovery.rs           # 启动器安装与可执行文件检测
├── pcl2.rs                # PCL2 适配器
├── hmcl.rs                # HMCL 适配器
├── mapping.rs             # 根目录、实例、启动器之间的显式映射
└── process.rs             # 进程创建、状态与错误反馈
```

SQLite 设计须能存储启动器安装项、根目录关联、实例启动映射、用户选择的默认启动器、能力检测结果（以及检测方式和版本），但不要存储账户令牌或任何敏感认证数据。避免把不同根目录下同名实例误认为同一实例。

### 功能验收测试（必须真实验证，不得只用 Mock 宣称支持）

1. 多个版本分别为 `1.21.11-Fabric_0.19.3`、`1.21.11-NeoForge_xxx`、`1.21.11`，能够正确区分，并从所选地图定位正确实例。
2. PCL2、HMCL 指向不同 Minecraft 根目录时，不会对错根目录发送启动请求；允许用户手动修正映射。
3. 未安装启动器、配置路径错误、无法找到 Java、实例已删除、目标处于共享游戏目录但没有唯一映射等情况，会明确提示，不会错误启动其他版本。
4. 已验证支持“外部启动指定版本”的启动器，实际点击后确实向**目标实例**发送有效启动请求；若能确认游戏进程，正确更新状态。未验证支持的启动器，只展示「打开启动器」，不得显示“已启动目标版本”。
5. 处理带空格、中文和特殊字符的启动器/实例路径，不通过 shell 拼接字符串；失败能看到实际错误信息。
6. 用假启动器可执行文件或 Test Adapter 验证参数、工作目录、回退状态的自动化测试；**此外**针对真实安装的 PCL2/HMCL 做人工集成测试，并将结果、启动器版本、限制写入 `TESTING.md`。
7. 运行中的游戏文件应得到写入保护或操作前风险警告；不破坏启动器的账号、Java 或隔离设置。

## 4. 交互与视觉体验

用户界面应克制、直观、紧凑，而非花哨。参考 Windows 11 文件资源管理器的实际工作流程，同时吸收 WinDirStat 的磁盘占用可视化。要求：

- 深色主题优先，可切换浅色主题（可后做）；
- 左侧稳定导航；顶部显眼的全局搜索框；中间可排序的数据表格；右侧可关闭的详情侧栏；
- 适度圆角、统一间距、清晰的文字层级，不滥用大卡片；
- 流畅滚动，滚动时不重复扫描目录；
- 窗口可自由改变大小，布局随宽度合理收缩，支持高 DPI；
- 列表表头点击排序，表格列可调整宽度（若框架允许）；
- 大量项目使用可复用行/虚拟化策略，避免一次创建成千上万复杂 UI 节点；
- 双击、右键、Esc、Delete、Ctrl+F 或 Ctrl+K、F5、Ctrl+A 等合理快捷键；
- 地图和游戏实例详情页增加「启动所在版本」按钮及启动器选择菜单，清晰区分「真正启动游戏」「仅打开启动器」「需手动关联」；
- 启动器配置、能力检测和启动请求状态有明确可见的 UI 反馈，禁止“请求已发出”就直接展示“启动成功”；
- 文件操作过程中显示进度、失败原因和可取消状态；
- 扫描中 UI 保持可交互，及时显示已识别的文件及“大小计算中”的状态；
- 任何磁盘 I/O、大批量 SQLite 查询和哈希计算不得直接在 UI 线程执行。

请先实现一个真正可点击、能读取用户文件夹的界面，而不是只画静态 UI 稿。

## 5. 文件操作安全规范（必须严格遵守）

**文件管理器具有破坏数据的能力，安全优先于功能数量。**

1. 第一阶段以只读扫描、搜索、查看、定位为主；不急于开放删除。
2. 删除默认移入 Windows **回收站**，而不是永久删除；只有当回收站方案经过验证后才能开放相应按钮。回收站不可用时必须给出明确提示，不得静默改为永久删除。
3. 删除、移动、覆盖前弹出确认对话框，列出真实源路径、目标路径、文件数/大小及可能影响的游戏目录。
4. 对游戏版本删除特别提供“仅删除该版本定义/核心文件”和“同时处理其独立实例目录”等清晰区分；**绝对不能默认连带删除共享 `saves`、`resourcepacks`、`mods` 等**。
5. 严禁删除 `.minecraft` 根目录、`versions` 根目录、磁盘根目录、用户主目录等高风险路径；实现路径保护与规范化校验，而不是只靠 UI 提示。
6. 禁止对跨文件系统移动、覆盖、重命名等操作在失败后留下不完整数据而假装成功；优先采用“复制到临时位置→校验→完成后处理原文件”的安全流程，失败时保留原件。
7. 移动/复制世界时检测目标重名与潜在冲突，默认不覆盖；必要时提供重命名选项。
8. 遇到正在被 Minecraft 使用的文件、权限不足、磁盘空间不足，明确错误信息和恢复建议。
9. 文件复制/移动过程中 UI 保持响应，支持取消（注意取消时的中间文件清理）。
10. 写操作后更新索引与界面状态；成功与失败都应有清晰反馈。
11. 备份世界采用复制或压缩归档，提供恢复方式；对压缩任务计算进度并防止归档失败误认为已备份。
12. 从头到尾以**用户本地文件隐私**为准则，绝不上传目录清单、NBT 数据、文件名到网络。
13. 从地图/版本页面启动 Minecraft 前要识别可能的文件占用；游戏正在运行期间，不允许默认对正在使用的世界执行删除、移动、覆盖等危险操作。启动器集成不触碰认证信息。

重复文件检测不能只按同名判断；先比较文件大小，用户主动启动检测时再计算文件哈希；“疑似重复世界”与“完全相同文件”分开描述，不得自动清理。

## 6. 扫描、索引、性能与异常处理

建议构建独立的扫描服务与 SQLite 索引：

- 初次扫描：枚举已经添加的根目录和实例，发现版本、游戏目录及各类内容；按阶段显示进度。
- 先识别条目，再分批读取元信息与统计目录大小；让用户尽快看到结果。
- 采用有上限的并行任务，避免同时打开过多文件导致磁盘抖动。
- 后续使用 `notify` 文件监控 + 定期/手动重新扫描作为补偿；监控事件丢失时可手动 F5 刷新。
- 将结果缓存在 SQLite；再次打开程序先显示可用缓存，后台校验变化。
- 数据库应包含足够的数据主键、规范化路径、目录归属、条目类型、名称、大小、时间、扫描状态等信息，并为搜索/排序建立适当索引。
- 路径是重要字段，但不要仅用文件夹显示名称充当主键；跨根目录允许重名。
- 首次扫描和刷新要能中断与重试；不因一个损坏 `level.dat`、锁定文件、权限异常而终止整个扫描。
- 世界目录的空间计算采用文件真实字节数；选择逻辑大小还是磁盘分配大小时要明确显示口径。默认优先统计逻辑文件大小，后续可扩展磁盘分配大小。
- 共享目录、符号链接等需去重处理，确保统计语义正确。
- 对无权限、移动中、断开的磁盘与路径失效状态给出清晰提示，不随意删除失效条目的收藏/标签记录。
- 完整日志仅记录诊断必需信息，日志滚动、体积受限，默认不记录世界中实际游戏数据。

**体验验收**：面对几十个版本、成百上千个世界/资源包/模组时，搜索和表格操作仍应顺畅；至少提供一个能模拟大规模目录的测试或压力测试。不要承诺未经测量的具体毫秒数与内存数字；请自行测量并报告。

## 8. 分阶段开发与验收顺序

### 阶段 1 — 必须首先交付的可用 MVP

实现：

1. 初始化 Rust + Slint 项目并确保能编译启动；
2. 现代化深色窗口、侧边栏、列表、搜索框、状态栏；
3. 手动添加/移除多个 Minecraft 根目录与自定义游戏目录；
4. 发现 `versions` 下的版本定义，识别共享目录及版本隔离目录；
5. 扫描全部世界并读取 `level.dat` 基本元信息；
6. 计算世界和版本/实例可解释的目录大小；
7. SQLite 持久化索引；
8. 「全部存档」支持全局检索、按大小/时间/名称排序、按实例筛选；
9. 选中世界展示详情、复制完整路径、在 Windows 资源管理器中定位；
10. 后台扫描进度、取消/刷新、异常容错；
11. 基本自动化测试 + Release EXE 构建；
12. 首次启动的空状态、目录不存在状态、扫描失败状态；
13. 设置页可配置 PCL2/HMCL 的程序路径与对应 Minecraft 根目录，为实例指定默认启动器；
14. 在版本/地图详情提供「打开启动器」和「启动所在版本」入口，未验证的直接启动能力必须显示 `OpenOnly` 或 `Unmapped` 并禁用真正的一键启动。

**验收场景 A**：在版本隔离实例 `versions/1.21.11-Fabric_xxx/saves/` 下放入一张叫“冒险地图”的世界，在其他版本目录放另一张同名世界。搜索“冒险”必须找到两个不同条目，并显示真实所属目录。

**验收场景 B**：在 `.minecraft/saves/` 下放入共享存档。该世界应在「全部存档」出现一次，不能虚构成每个 Minecraft 版本各有一份。

**验收场景 C**：一张世界的 `level.dat` 损坏或缺失，程序不能崩溃；仍能显示目录名、路径与可统计大小。

**验收场景 D**：目录含中文和很长的名称时，搜索、定位、排序正常。

**验收场景 E**：对真实大目录后台扫描期间，拖动窗口、切换页面、输入搜索时界面不冻结。

**验收场景 F**：用户已经设置 PCL2 或 HMCL，能从地图详情页找到对应实例，并打开指定启动器；如果还不具备真正的外部指定实例启动能力，则明确告诉用户尚不能直接启动，而非运行错误的版本。

在通过以上验收前**不要开始设计复杂 Treemap 动画或批量删除**。

### 阶段 2 — 完善全局内容管理

- 全部资源包、模组、光影包及世界数据包索引；
- `pack.mcmeta`、JAR 基础元信息与图标预览；
- 统一搜索、按大小排序、按版本/实例筛选；
- 用户收藏/标签、最近打开；
- 文件监控与增量索引刷新；
- 只读重复文件候选检测；
- **优先完成 PCL2 / HMCL 的外部指定实例启动接口调研、能力适配和真实测试：能可靠启动时开放「启动所在版本」；不能可靠启动时保留「打开启动器 + 目标实例提示」降级流程，并在文档明确限制**；
- 为每个实例记录默认启动器，提供多启动器切换与启动失败回退。

### 阶段 3 — 安全的增删查改

- 重命名、复制、移动、备份；
- 经过验证的 Windows 回收站删除；
- 多选与批量操作、冲突处理、错误恢复；
- 版本删除时明确区分核心版本文件与独立游戏数据；
- 操作后的索引同步与必要的取消支持。

### 阶段 4 — 可视化和打磨

- WinDirStat 风格交互式 Treemap；
- 可视化统计图和空间清理建议；

## 10. Codex 工作方式（很重要）

1. **先检查当前工作区和本机开发环境**，确认 Rust、Cargo、Windows 编译工具链等是否可用。
2. 先给出简明的实施计划、目录结构和第一阶段任务拆分，再实际开始写代码。
3. 优先完成可运行的**阶段 1 MVP**，而不是只输出一堆设计文档、空函数或静态假数据。
4. 为每个功能编写实际逻辑；不允许使用“TODO”替代核心扫描、查找、排序、大小统计。
5. 项目代码量较大时可分多次实施，但每次都尽量保持项目可编译可运行。
6. 修改已有代码前先阅读关联模块，不要为了修一个小问题重写整个工程。
7. 遇到 Slint API、Windows API、NBT 或依赖库版本差异，请以当前安装版本的实际 API 与编译结果为准；必要时查阅官方文档，不要凭空编造调用方式。
8. 对于某个启动器的隔离规则、配置文件或映射关系，如无充分依据，**宁可标记未知并允许手动指定，也不要猜测目录归属**。

9. 每阶段完成后提供：已实现功能、未实现功能、构建/测试结果、运行方法、下一步计划。
